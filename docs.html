Learn C by watching it run

libft Lens is a practice space for the 42 projects libft, ft_printf and get_next_line. You write each function yourself; the app runs it as you type and shows what it does to memory, line by line. When you are stuck it gives you the next idea, not the answer.

Quick start

  1. Pick a project (libft, ft_printf or get_next_line), then a step on the rail. libft goes from easy (ft_isalpha) to hard (ft_lstmap); ft_printf and get_next_line are split into helpers first, then the function the subject asks for.
  2. Read the goal and the prototype, then replace the /* ▢ 1: … */ placeholders with your own code. Each placeholder is one step of the plan.
  3. Stop typing for half a second: your code runs against the selected test. Press Next or Play to watch it, or click a line to see memory at that moment.
  4. When every test is green, move on with Next: ….

Everything runs in your browser. There is nothing to install and no account.

Reading memory

Each function call has a stack frame with its variables. The frame with a blue outline is the one running. Below the frames, every array, string literal and malloc block is drawn as a row of cells, one per element.

  • Read: the last line read this cell.
  • Written: the last line changed this cell.
  • '\0': the terminator that ends a C string.
  • Never written: the cell holds garbage until you set it.
  • Out of bounds: a cell past the end of a block that your code touched. It does not belong to you.
  • Leaked: a heap block nothing points to any more, so it can never be freed.

Arrows are pointers. A dot in a variable is where the pointer is stored; the arrow ends at the cell it points to. Small labels above cells (s, dst, s[i]) name what points there or what was just accessed.

When you step forward one line, changes animate: new frames drop in and returning frames slide away, arrows glide when a pointer moves, values flip, a copied byte flies from its source to its destination, new heap blocks grow in and freed ones crumble. Stepping back and dragging the slider stay instant. Turn animations off with the switch in the header; your system's "reduce motion" setting turns them off too.

Three more boxes appear when your code needs them:

  • Static memory (dashed): static variables and globals. They live outside every call, so this is where get_next_line's stash survives from one call to the next.
  • Open files: each file your code opened, byte by byte. What read() has already consumed is dimmed and next marks the next byte, up to EOF.
  • The ... row in a variadic function's frame: the extra arguments of this call. Used ones are crossed out and the one the next va_arg will take is highlighted; a va_list variable shows which argument comes next.

Expert view adds addresses, element types and byte details. The default view hides them so the shapes are easier to read.

Getting unstuck

Help comes in small doses, and you decide when.

  1. Stuck? Ask me a question gives a question that points at the idea, then the concept behind it.
  2. Each step of the plan reveals in levels: what the step achieves, a plain-language description, the C with blanks (while (s[__] != __)), and finally the code with a Put it in my code button.

Revealing full code marks the exercise as assisted on the rail (a ring around its mark). Nothing is revealed unless you ask. If you used the code, try writing the function again from scratch a day later: that is when it sticks.

What is checked

Behaviour
Each exercise has tests from the subject and the man pages. ft_printf is compared character by character with the real printf, return value included (a NULL %p may print (nil) or 0x0). get_next_line is tested with several BUFFER_SIZE values (1, 2, 3, 4, 42, 9999), files with and without a final newline, empty files, standard input and bad file descriptors; the bonus tests (several files at once) are optional and marked as bonus. including edge cases (empty strings, overlapping memory, INT_MIN, size 0). Functions that allocate are also tested with malloc failing: they must return NULL and free everything they already allocated.
Memory
Every test fails on a memory error or a leak, even when the result is right. The subject gives 0 for a crash or a leak.
Prototype and allowed functions
Your prototype must match the subject exactly, and you may only call the functions the subject allows plus your own libft functions.
Compiler
Problems that make cc -Wall -Wextra -Werror refuse your file: unused variables and parameters, a function called before it is declared, and comparing signed with unsigned values.
Subject rules
libft: no global variables, and helper functions must be static. get_next_line: no global variables, and your libft is not allowed (calls to it are flagged and not linked). ft_printf may use your libft.
Norm (partial)
Line length, trailing spaces, tabs for indentation and alignment, space after if/while/return, return (value);, no comments inside functions, at most 25 lines, 4 parameters, 5 variables and 5 functions, declarations at the top and not initialised, one declaration per line, no for.

A green exercise here is strong evidence, not a guarantee. Always confirm with the real cc -Wall -Wextra -Werror, norminette, and your own tests before you submit.

Bugs it catches

Each one stops the run at the exact line with an explanation in plain words:

  • Reading or writing past the end of an array or a malloc block
  • Dereferencing NULL
  • Using memory after free
  • Freeing twice, or freeing a pointer malloc did not return
  • Writing into a string literal
  • Using a pointer to a local variable after its function returned
  • Using a variable before giving it a value
  • A function that ends without returning a value
  • Division by zero and out-of-range shifts
  • Signed overflow (a warning, since it is undefined behaviour)
  • Loops that never end, runaway recursion, and memory leaks

Supported C and limits

The app runs your code with an interpreter built for libft, modelling a 64-bit Mac or Linux machine (char is signed, long and pointers are 8 bytes).

Supported: all integer types, size_t, pointers, arrays, structs, typedef, function pointers, static locals, variadic functions with va_list/va_start/va_arg/va_copy/va_end, every operator, if/while/do/for, break/continue, string and character escapes, simple #defines and #if/#ifdef/#ifndef/#else/#endif (tests set BUFFER_SIZE like cc -D). #include lines are skipped; t_list is provided when your file uses it.

Built-in libc for your tests: malloc, calloc, free, write, read, open, close, printf, puts, putchar and the usual string, memory and ctype functions. Files exist only in memory: the tests create them.

Not yet: float/double, union, enum, switch, goto and macros with arguments.

Limits: 300,000 steps per run, 20,000 allocations, 1 MB per allocation, 64 KB of output, 400 nested calls, and the first 3,000 steps are recorded for stepping.

Privacy and your data

Your code never leaves your computer. It runs in your browser, in a background worker. Your files, progress and settings are kept in this browser's local storage and nowhere else: clearing site data, or a private window, starts you fresh.

Pass marks are rebuilt every time the app opens by re-running your saved code, so they always reflect what your code really does.

FAQ

Is this allowed at 42?

The subject asks you to reason before reaching for help and never to ask for direct answers. libft Lens is built around that: it shows what your own code does and holds answers back until you ask several times. Check your campus's rules if you are unsure.

Why can I find the solutions in the source code?

The app has no server, so everything it can reveal ships with the page. It is a learning tool, not an exam: the only person you can fool is yourself, and the exam has no internet.

My code works on my Mac but fails here. Who is right?

Usually the app: undefined behaviour such as reading one byte past a block often "works" on a real machine by luck and then fails during evaluation. If you think the app is wrong, please open an issue with the code.
